# Screen contracts for presentation work

**Integration update:** The seven Gemini view prop interfaces in `apps/guard/src/ReportIncidentScreen.tsx` and `apps/guard/src/screens/` are the current compiled presentation contracts. `apps/guard/src/screen-contracts.ts` re-exports them; `apps/guard/src/presentation-adapter.ts` maps local and server rows. The table below records the earlier handoff baseline. Current service wiring and the limited server history/follow-up read are described in [GEMINI_INTEGRATION_REPORT.md](GEMINI_INTEGRATION_REPORT.md).

These are the present runtime contracts. Route names are logical IDs from `NAVIGATION_MAP.md`. All data is scoped to the signed-in user by Supabase/RLS or by `author_id` in encrypted local SQLite. UI code receives state and callbacks; it must never call Supabase RPCs or manipulate the SQLite outbox directly.

## Shared types and state rules

Guard TypeScript types are in `apps/guard/src/screen-contracts.ts`, `incident-domain.ts` and `offline.ts`. `Duty` carries `shift_id`, `site_id`, `site_name`, `guard_id`, `started_at`, `ended_at`, `fetched_at`. `LocalRecord` carries UUID, kind, payload, author/site/shift IDs, state, local save time, nullable server receipt time/reference and nullable error. `RecordState` is `queued | sending | failed | received`. Server acknowledgement is a **separate** incident lifecycle state and is currently unavailable in guard details. Never derive it from `received`.

Every data screen needs loading, empty, refresh-error-with-existing-data, and content states. Offline duty may be displayed as **previously verified**; a local save must show pending until the real RPC receipt is confirmed. `sending` means awaiting receipt; after interruption the same UUID retries. Errors remain recoverable. Form drafts survive save failure. Required touch targets are at least 48 px.
